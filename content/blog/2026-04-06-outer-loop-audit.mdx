The first version of this tool scored GitHub orgs on a 0-100 scale across five dimensions, split into four persona views, and produced reports that said things like "your CI health score is 52." It worked. Nobody cared about the score.

The problem was legibility. A composite score requires the reader to trust your weighting model, and cold prospects don't trust you yet. They'd look at "52/100" and ask "compared to what?" — which meant we needed benchmarks, which meant we needed data we didn't have, which meant we were making stuff up. Alex's PRD cut through all of that: show the raw numbers, let the numbers speak, attach each number to a Trunk product that fixes it.

## The rewrite

The new version is a single-repo audit. No org aggregation, no persona switching, no composite scores. You authenticate via a GitHub App (read-only, no code access), type an `owner/repo`, and get back 10 metrics in two groups.

Five headline metrics, each with a big number, a one-line explanation, expandable methodology, and a product CTA:

1. **CI Failure Rate** — % of workflow runs on the default branch that failed
2. **Re-run Rate** — % of runs with `run_attempt > 1` (the behavioral fingerprint of flaky tests)
3. **P90 Time to Merge** — 90th percentile PR creation-to-merge, with P50 for comparison
4. **CI Duration Trend** — weekly median run duration over 90 days, rendered as a sparkline
5. **PRs per Committer per Day** — velocity proxy that frames the "AI is making more PRs" problem

Five deeper insight cards in a compact grid: total CI minutes consumed, active workflow count, noisiest workflows by failure rate, queue saturation (P90 wait time), and trigger breakdown (push vs PR vs schedule).

## Architecture decisions that mattered

**Bot filtering everywhere.** Dependabot and Renovate generate a ton of CI activity that doesn't reflect human engineering velocity. Every metric filters bots out by default and reports what was excluded. This alone changed the numbers dramatically for repos with active dependency bots.

**Adaptive lookback.** A repo with 50 runs/month gets the full 30-day window. A repo with 3,000 runs/month gets shrunk to ~10 days so we stay under the API budget. The first page of results estimates the density, and we adjust before paginating further. This is disclosed in the report header.

**API budget tracking.** Each audit gets 500 API calls. The fetcher checks the budget before every request and stops gracefully instead of hitting rate limits. Trend data uses a sampling strategy — one page per week over 90 days (13 calls) instead of paginating the full history.

```python title="Adaptive lookback estimation"
def estimate_lookback_days(first_page_count, first_page_days_covered,
                           target_sample=1000, max_lookback=30, min_lookback=7):
    runs_per_day = first_page_count / first_page_days_covered
    estimated_total = runs_per_day * max_lookback
    if estimated_total <= target_sample * 3:
        return max_lookback
    ideal_days = max_lookback * target_sample / estimated_total
    return max(min_lookback, math.floor(ideal_days))
```

**Conditional CTAs.** The first version showed "fix this with Flaky Tests" even when the rerun rate was 0%. Alex caught this immediately. Now CTAs only appear when the metric indicates an actual problem — failure rate above 2%, rerun rate above 2%, P90 merge time over an hour.

## The OAuth flow

GitHub App OAuth instead of personal access tokens. The app requests `actions:read`, `checks:read`, `pull_requests:read`, and `metadata:read` — nothing else. The backend handles the code exchange and stores sessions in memory with an 8-hour expiry.

One thing that bit us: the GitHub OAuth callback URL (`/auth/callback`) collided with the Vite dev proxy. GitHub redirects the browser to that URL, but the React SPA also needs to load there to read the `code` parameter. The fix was renaming the backend endpoint to `/auth/exchange` so the proxy doesn't intercept the browser redirect.

## Deploying to Vercel (and everything that broke)

Vercel serves static files directly from the frontend build and routes API calls to a Python serverless function. Sounds simple, but serverless has opinions about state:

- **Read-only filesystem.** The file-based cache can't write. Wrapped all cache writes in `try/except OSError` — cache becomes a no-op in serverless.
- **No shared memory.** The in-memory session store and CSRF state tokens don't survive between function invocations. OAuth state validation had to be relaxed — the code exchange with GitHub is the real security check anyway.
- **Password gate.** Server-side middleware can't gate static files (Vercel serves them before hitting the function). Moved the gate to the frontend — an API endpoint validates the password, React shows the form.

The dev experience is still local FastAPI + Vite with hot reload. Vercel is for sharing the demo.

## The GitHub OAuth rabbit hole

Account switching in GitHub OAuth is not a thing. GitHub uses whatever account is logged into the browser. If you sign out of the app and sign back in, GitHub auto-approves because you're still logged in as the same user. The only way to switch is to literally log out of github.com.

We ended up with a "Switch GitHub account" button that clears the app session, revokes the OAuth grant via GitHub's API, opens github.com/logout in a new tab, and returns the app to the landing page. Not elegant, but honest about the platform constraint.

The repo listing endpoint was another surprise. `GET /user/installations/{id}/repositories` returns repos where *both* the app is installed *and* the user's OAuth token has access. So even if an org admin installs the app on all repos, users who aren't org members only see repos they have direct access to. The dropdown shows what it can; the text input works for anything the app can reach.
